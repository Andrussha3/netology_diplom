# План проверки и автоматизации приложения «В Хосписе»

## 1. Объект и цель тестирования

Объект тестирования — Android-приложение «В Хосписе» версии 1.0.0
(`applicationId: ru.edu.qamid`). Цель — проверить основные пользовательские
сценарии, подготовить воспроизводимый набор ручных проверок и основу для
последующей автоматизации UI-тестов.

Тестовая учётная запись:

- логин: `login2`;
- пароль: `password2`.

Целевая конфигурация: Android API 36, русская локаль, портретная ориентация.
Сборка проекта выполняется в Podman-контейнере с JDK 17 и Android SDK 36.

## 2. Границы приложения

В объём проверки входят:

1. Стартовый экран и восстановление сохранённой сессии.
2. Авторизация и негативные сценарии входа.
3. Главный экран: последние три новости, сворачивание блока, обновление.
4. Навигация через главное меню и верхнюю панель.
5. Список новостей: отображение, раскрытие карточки, сортировка, обновление.
6. Фильтрация новостей по категории и диапазону дат.
7. Панель управления новостями для администратора.
8. Создание, редактирование, включение/выключение и удаление новости.
9. Фильтрация панели управления по категории, датам и активности.
10. Раздел «Наша миссия»: список из восьми цитат, раскрытие и сворачивание.
11. Выход из учётной записи.
12. Основные состояния ошибок сети, загрузки и валидации полей.

За границами текущей работы:

- серверное API и его нагрузочное/безопасностное тестирование;
- проверка административной панели вне мобильного приложения;
- iOS и Android ниже API 23;
- восстановление пароля, регистрация и изменение профиля — такого функционала
  в приложении нет;
- этапы автоматизации и Allure до согласования первого этапа.

## 3. Анализ реализованного функционала

По навигации, ресурсам и исходному коду выявлены экраны: splash,
«Авторизация», «Главная», «Новости», «Фильтрация новостей»,
«Панель управления», «Создание/редактирование новости» и «Наша миссия».

Категории новостей: «Объявление», «День рождения», «Зарплата», «Профсоюз»,
«Праздник», «Массаж», «Благодарность», «Нужна помощь».

Обязательные поля новости: категория, заголовок, дата публикации, время и
описание. Для новой новости активность включена и недоступна для изменения.
Дата публикации выбирается не раньше текущей. При отмене редактирования
показывается предупреждение о несохранённых изменениях.

## 4. Виды тестирования

- функциональное: позитивные и негативные пользовательские сценарии;
- UI: наличие, состояние и читаемость элементов, длинные тексты, прокрутка;
- навигационное: переходы между всеми доступными экранами и возврат;
- совместимость: обязательный прогон на Android API 36;
- сетевое: отсутствие сети, ошибка авторизации, повтор загрузки;
- сохранность данных: сессия после перезапуска, CRUD новостей;
- исследовательское: быстрые повторные нажатия, смена ориентации, фон/возврат;
- регрессионное: повтор критических сценариев после исправлений.

Нагрузочное тестирование backend, pentest и полноценная accessibility-аудит
не входят в первый этап. Базовые проверки accessibility (content description,
размеры областей нажатия, контраст и масштаб шрифта) выполняются вручную.

## 5. Тестовый подход

Приоритет определяется риском:

- P0: запуск, вход, доступ к основным экранам, выход;
- P1: чтение, фильтрация и CRUD новостей;
- P2: сортировка, обновление, цитаты, обработка ошибок;
- P3: косметика, ориентация, масштаб шрифта и исследовательские проверки.

Техники тест-дизайна:

- классы эквивалентности для валидных/невалидных реквизитов входа;
- граничные значения и переходы состояний для обязательных полей и дат;
- таблица решений для пары дат и двух флагов активности;
- переходы состояний для сессии и активности новости;
- сценарии использования для навигации и CRUD.

Данные для CRUD должны быть уникальны, например
`Диплом QA <дата-время>`, чтобы созданную запись можно было однозначно найти и
удалить. После каждого изменяющего теста данные возвращаются в исходное
состояние.

## 6. Окружение и инструменты

- JDK 17 и Android SDK 36;
- Gradle Wrapper 8.13;
- Android Emulator API 36 либо физическое устройство с Android API 36;
- Android Studio и `adb` для установки APK и сбора логов;
- сеть с доступом к `https://students.netoservices.ru/`.

Перед ручным прогоном выполняются сборка `assembleDebug`,
установка APK, очистка данных приложения и проверка доступности backend.

## 7. Порядок работ

1. Собрать debug APK и установить на устройство API 36.
2. Выполнить smoke-набор P0.
3. Пройти `Check.csv`, фиксируя `PASSED`, `FAILED`, `BLOCKED` или `NOT_RUN`.
4. Для дефектов записать шаги, фактический и ожидаемый результат, окружение,
   скриншот/видео и фрагмент logcat.
5. Уточнить `Cases.csv` по результатам исследовательского тестирования.
6. После согласования первого этапа определить набор UI-тестов по полю
   `Автопокрытие` и перейти к автоматизации.

## 8. Критерии начала, остановки и завершения

Начало: проект получен, debug APK собирается, доступно устройство API 36,
backend отвечает, тестовая учётная запись активна.

Остановка: приложение не устанавливается/не запускается, backend или учётная
запись недоступны, обнаружен блокирующий дефект P0. После устранения причины
выполняется повторный smoke.

Завершение первого этапа:

- выполнены все доступные проверки P0–P2;
- для каждого пункта указан статус и доказательство либо причина блокировки;
- заведены обнаруженные дефекты;
- тестовые новости удалены;
- актуализированы `Plan.md`, `Check.csv` и `Cases.csv`.

## 9. Риски

- роль пользователя `login2` и набор серверных данных могут измениться;
- зависимость от сети делает результаты нестабильными;
- удаление новости необратимо, поэтому удаляются только записи текущего теста;
- отсутствие аппаратной виртуализации может не позволить запустить эмулятор.

## 10. Предварительная оценка

- анализ и актуализация документации: 8 часов;
- развёртывание и smoke: 4 часа;
- функциональный ручной прогон: 6 часов;
- исследовательская проверка и дефекты: 3 часа;
- повторный прогон после исправлений: 3 часа.

Итого для первого этапа: около 24 часа без учёта ожидания исправлений.
